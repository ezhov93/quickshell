## Context

Сейчас `shell/config/Config.qml` содержит команду `foot -e nmtui` для сетевых настроек. У shell уже есть граница конфигурации и сервис `NetworkService`, но общего разрешения приложений по ролям нет. См. мотивацию в `proposal.md`; текущую команду в этом change не меняем.

## Goals / Non-Goals

**Goals:**

- Ввести роль приложения как устойчивый контракт между системным действием и конкретным launcher.
- Сравнить XDG associations, переменные окружения и пользовательскую конфигурацию по переносимости и диагностируемости.
- Обеспечить корректный запуск TUI-команд через терминал с массивом аргументов.
- Сохранить низкую стоимость: без фонового процесса, polling и обязательного нового daemon.

**Non-Goals:**

- Не менять текущий `foot -e nmtui` до отдельного применения этой capability.
- Не устанавливать терминалы или другие пакеты.
- Не менять системные MIME associations автоматически.
- Не проектировать полный менеджер сессии или настройки всех приложений пользователя.

## Decisions

### 1. Ввести role-based разрешение

Потребители запрашивают роль (`terminal`, позднее `browser`, `file-manager`, `editor`), а не знают имя бинарника. Граница должна находиться в конфигурационном/сервисном слое shell; UI передаёт только роль и аргументы операции.

Альтернатива — хранить команды в каждом компоненте — отвергнута из-за дублирования и привязки к одной машине.

### 2. Разделить графические и TUI-роли

Для графических документов и URL предпочтительны XDG MIME/application associations: они учитывают desktop entry и пользовательский выбор. Для терминала и TUI-команд XDG не задаёт полного переносимого контракта запуска, поэтому нужен отдельный шаблон терминала с executable и аргументами.

Альтернатива — использовать `xdg-open` для `nmtui` — отвергнута: `xdg-open` открывает URI/файлы и не описывает запуск интерактивной команды внутри терминала.

### 3. Environment использовать только как fallback

Явная пользовательская настройка имеет высший приоритет. Для терминала можно поддержать `TERMINAL` как совместимый fallback, затем системный/проектный fallback. Поскольку `TERMINAL` не гарантирует формат аргументов и не является универсальным стандартом, значение проверяется как executable, а параметры `-e`/эквивалент задаются отдельным профилем или настройкой.

Альтернатива — сделать `TERMINAL` единственным источником — отвергнута из-за неодинакового поведения терминалов и отсутствия гарантии запуска команды.

### 4. Хранить команды как структурированные argv

Разрешённое приложение и аргументы передаются массивом элементов, а не строкой shell-команды. Это сохраняет пробелы и исключает лишнюю shell-интерпретацию. Для TUI-профиля отдельно задаётся позиция команды и аргументов.

### 5. Ошибка не ломает shell

Проверка доступности выполняется при запросе или при загрузке конфигурации без запуска фонового watcher. Если значение недоступно, resolver переходит к следующему источнику; если источники исчерпаны, сервис сообщает ошибку через журнал/сигнал, а UI остаётся рабочим.

## Risks / Trade-offs

- [Риск] Разные терминалы принимают разные параметры запуска → [Митигация] хранить профиль запуска структурированно и проверять его на реальной машине.
- [Риск] Environment может быть унаследован неполно в session/systemd → [Митигация] явная пользовательская настройка и диагностический источник значения.
- [Риск] XDG desktop entry может существовать, но быть непригодным для конкретной операции → [Митигация] проверять роль и сценарий отдельно; не использовать XDG для TUI.
- [Риск] Проверка `command -v` не гарантирует успешный запуск → [Митигация] обрабатывать ошибку создания процесса и не считать доступность доказанным запуском.

## Migration Plan

1. Зафиксировать контракт роли и приоритет источников в baseline spec после согласования.
2. Реализовать resolver/service без изменения потребителей.
3. Перевести сетевые настройки на resolver и сохранить эквивалентный запуск `foot -e nmtui`.
4. Проверить отсутствие конфигурации, environment, terminal и диагностировать недоступные источники.
5. Откатить можно удалением resolver и возвратом явной команды в `Config.qml`; пользовательские настройки не удаляются.

Первая реализация ограничивается ролью `terminal`; browser, file-manager и editor добавляются позднее тем же контрактом. Пользовательское переопределение первой версии хранится в отдельной настройке shell, а XDG associations подключаются только для будущих графических ролей.
