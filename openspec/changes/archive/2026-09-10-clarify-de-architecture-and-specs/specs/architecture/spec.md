## MODIFIED Requirements

### Requirement: UI зависит от сервисов и интеграций через устойчивые слои

Модули оболочки MUST использовать переиспользуемые визуальные компоненты и сервисы; переиспользуемые компоненты MUST NOT зависеть от использующих их модулей. Сервисы MUST обращаться к системным возможностям через поддерживаемые API Quickshell или адаптеры. Отдельный адаптер не обязателен, если сервис уже обеспечивает нужную границу интеграции. Известные нарушения этого ограничения в существующем коде учитываются отдельно, а не объявляются соответствием.

#### Scenario: Возможности shell требуется системное состояние

- **WHEN** модуль отображает или изменяет состояние системной возможности
- **THEN** он использует предоставляемое сервисом состояние и операции; сервис не зависит от визуальных компонентов

#### Scenario: Используется готовая интеграция Quickshell

- **WHEN** поддерживаемый API Quickshell достаточен для ответственности сервиса
- **THEN** архитектура допускает его использование сервисом без промежуточного адаптера, не имеющего собственной ответственности

### Requirement: Визуальные компоненты не владеют системной интеграцией

Визуальные компоненты MUST NOT самостоятельно выполнять системные операции через процессы, D-Bus или IPC и MUST NOT владеть общим системным состоянием. Локальное состояние представления, включая наведение, фокус и черновик редактирования, допускается в UI или контроллере модуля. API Qt/Quickshell для создания окон, отрисовки и ввода не считаются запрещённой системной интеграцией.

#### Scenario: Визуальный элемент изменяет системное состояние

- **WHEN** пользователь активирует элемент управления системной возможностью
- **THEN** элемент передаёт запрос сервису или контроллеру модуля, отвечающему за эту операцию

#### Scenario: Пользователь редактирует черновик

- **WHEN** пользователь меняет выбор или положение элементов в ещё не применённой форме
- **THEN** UI может хранить этот черновик локально, не объявляя его подтверждённым состоянием внешней системы

### Requirement: Системное взаимодействие предпочитает нативные событийные интерфейсы

Для системного взаимодействия проект MUST выбирать поддерживаемые нативные API, IPC или D-Bus, если они предоставляют необходимую операцию, и использовать надёжные события об изменениях вместо дублирующего опроса. Если нужный интерфейс отсутствует или непригоден, причина использования внешней команды или опроса MUST быть указана в описании интеграции или изменении.

#### Scenario: Внешнее состояние изменяется

- **WHEN** интеграция предоставляет надёжное событие нужного изменения
- **THEN** сервис использует это событие и не добавляет для того же изменения необоснованный постоянный опрос

#### Scenario: Для операции доступна только внешняя команда

- **WHEN** поддерживаемые API не предоставляют необходимую операцию
- **THEN** вызов команды допускается на границе интеграции с указанной причиной, а не переносится в переиспользуемый визуальный элемент

### Requirement: Опрос ограничен и обоснован

Для каждого механизма опроса MUST быть определены причина, интервал и условие активности. Опрос, обслуживающий только скрытый интерфейс, MUST останавливаться, когда у данных нет других активных потребителей. Скрытое окно или индикатор не означает отсутствия потребителя: обнаружение внешнего изменения для показа OSD является активной ответственностью сервиса.

#### Scenario: Резервный опрос поддерживает неактивную возможность shell

- **WHEN** панель скрыта и её статистика ресурсов больше не нужна другим возможностям
- **THEN** связанный с этой статистикой опрос не продолжается

#### Scenario: OSD ожидает внешнее изменение яркости

- **WHEN** OSD скрыт, но должен показать следующее внешнее изменение яркости, а надёжных файловых событий недостаточно
- **THEN** общий сервис может продолжать обоснованный ограниченный опрос устройства

### Requirement: Границы собственного и внешнего программного обеспечения разделены

Проект MUST различать собственную конфигурацию и программный код, объекты сервисов внутри Quickshell и внешние процессы дистрибутива. Каталог QML-сервисов MUST NOT трактоваться как набор самостоятельных демонов. Собственная интеграция не означает владения внешним компонентом.

#### Scenario: Добавляется новая системная возможность

- **WHEN** новая возможность может использовать существующую платформенную службу
- **THEN** проект описывает конфигурацию или интеграцию с ней, а необходимость дополнительного собственного процесса оценивает отдельно

### Requirement: Новые custom daemon требуют явного архитектурного обоснования

Проект MUST NOT добавлять собственный постоянно работающий демон без объяснения, почему существующая конфигурация, сервис внутри Quickshell, unit-файл systemd или внешний API не решают задачу. Обоснование MUST определять ответственность, необходимые привилегии, владельца запуска, завершение процесса и ожидаемую ресурсную стоимость.

#### Scenario: Для новой возможности предлагается фоновая работа

- **WHEN** для возможности предлагается собственный демон
- **THEN** до реализации рассматриваются альтернативы и фиксируются границы процесса; само наличие каталога для сервисов не является обоснованием

### Requirement: Спецификации возможностей ориентированы на capability

Спецификации MUST описывать возможности DE, наблюдаемое поведение и проверяемые сквозные ограничения, а не повторять исходные каталоги. Места реализации и объяснения решений MUST размещаться в архитектурной документации и материалах изменения, если путь сам по себе не является внешним контрактом.

#### Scenario: Одна возможность проходит через несколько слоёв проекта

- **WHEN** изменение затрагивает пакеты, конфигурацию, интеграции, сервисы и UI
- **THEN** требования группируются по затронутым возможностям, а связи с исходниками указываются отдельно
