## Context

Мотивация и область изменения описаны в [proposal.md](proposal.md). Исследован существующий проект на основе ревизии `48e77ed`, включая незакоммиченные пользовательские документы. Сам change содержит предложения, а не уже применённую архитектуру.

Сейчас корневой `shell.qml` объединяет семь модулей, QML-сервисы работают внутри Quickshell, установщик копирует QML и `qmldir`, а `extra/hypr/` содержит не разворачиваемый установщиком примерный профиль. Автоматического тестового framework, CI и установщика всего DE нет.

`design.md` необходим: изменение затрагивает несколько связанных спецификаций и маршрутизацию инструкций агенту; без единой схемы документов появятся новые противоречия.

Обнаруженные конфликты контекста разрешаются явно в рамках запрошенного пересмотра: направление `components -> modules` исправляется, требование русскоязычных документов получает исключение для англоязычного `AGENTS.md`, а целевое дерево каталогов больше не описывается как существующее. До применения change прежние документы не переписываются.

## Goals / Non-Goals

**Goals:**

- После применения агент может найти действующий контракт, конкретный источник, ограничения задачи и способ проверки без восстановления договорённостей из переписки.
- Формулировки нормативных требований отделены от доказательств соответствия им. Известный дефект остаётся дефектом, а не превращается в разрешённое поведение ради зелёного отчёта.
- Карта документации компактна: подробности читаются по задаче, а не все документы на каждом шаге.
- Каждая задача этого change имеет конечный документальный результат; завершение не зависит от запуска рабочего стола или выбора будущей платформы развёртывания.

**Non-Goals:**

- Любые изменения QML, публичного IPC, установщика, профиля Hyprland или настроек машины.
- Переезд QML в `shell/` или `configs/quickshell/`, создание package-манифестов, unit-файлов, D-Bus-контрактов, новых служб или тестов.
- Выбор версии Debian, session manager, тестового framework, численных ресурсных бюджетов или формата пользовательских настроек.
- Исправление отображения markup, конфигурации блокировщика или переноса состояния обоев в этом change.
- Обновление навыков `.agents/`, выбор моделей, коммит, автоматическое архивирование и выполнение планов из `PLANS.md`.

## Decisions

### D1. Разделить документы по ответственности, не переносить runtime-код

После применения структура документов должна быть следующей. Указанные новые пути — задачи этого change, а не заявление об их нынешнем существовании.

| Файл | Что создать или изменить | Что не помещать сюда |
|---|---|---|
| `docs/README.md` | Указатель: продукт, архитектура, требования, статус, тестирование, процесс, roadmap, история | Копию всех правил |
| `docs/project-context.md` | Краткое описание продукта, владение, цели/нецели, оборудование, фактический этап и целевые дистрибутивы | Большое целевое дерево и несуществующий корневой `specs/` |
| `docs/architecture.md` | Текущие компоненты и процессы, зависимости, данные, внешние интерфейсы, установка и границы сессии; правила со ссылками на спеки и ADR | Обещание уже выполненной миграции или подробную очередь задач |
| `docs/spec-status.md` | Доказательства и состояние соответствия каждого требования, проверки, известные пробелы | Вторую копию нормативного текста |
| `docs/testing.md` | Существующие проверки, будущие проверки, безопасные условия, формат результатов и критерий завершения | Выдуманные тесты, команды невыбранных инструментов или утверждение, что непроверенное прошло |
| `docs/openspec-workflow.md` | Практический цикл изменения и правила разрешения неоднозначностей | Обязательный порядок слоёв для любой задачи или общую копию архитектуры |
| `docs/roadmap.md` | Этапы после документального фундамента, зависимости этапов и решения, нужные перед каждым | Утверждение, что будущие требования уже приняты или реализованы |
| `docs/adr/0001-de-product-boundary.md` | Почему продуктом является DE, а внешние компоненты не переопределяются проектом | Новые обязательные внешние зависимости |
| `docs/adr/0002-modular-quickshell-shell.md` | Почему базовый вариант — модули одного процесса, правильные зависимости и необязательные адаптеры | Обещание полного соответствия существующего UI этим границам |
| `AGENTS.md` | Короткий алгоритм работы, актуальные пути и предохранители | Устаревшие имена темы/сервиса и утверждение, что название модели гарантирует качество |
| `openspec/config.yaml` | Краткий контекст, ссылки и правила качества артефактов | Параллельную спецификацию поведения и скопированные перечни из контекста |
| `README.md` | Уточнение текущей поставки и ссылка на `docs/README.md`; сохранить проверенные команды | Заявление об установке всего DE |
| `PLANS.md` | Только статусное пояснение: прежний список идей, не активный change; ссылка на roadmap | Выполнение задач TuneD или удаление истории |

`docs/architecture-review.md` оставить без изменения как датированный исходный разбор. Ссылаться на него из указателя как на историю, не как на действующую инструкцию.

Альтернативы: один большой документ сохраняет дублирование; крупное дерево из десятков архитектурных файлов повышает стоимость чтения. Выбран ограниченный набор документов с разными обязанностями. Перенос runtime-кода отложен, поскольку текущий установщик сохраняет относительные пути всех найденных QML и такой перенос изменит поставку.

### D2. Определить порядок чтения и разрешения конфликтов

В `AGENTS.md` и руководстве описать алгоритм:

1. Прочитать `AGENTS.md`, продуктовый контекст и архитектуру; через `docs/README.md` найти остальные документы по необходимости.
2. Определить вид задачи: исследование, изменение документации, предложение нового поведения или применение существующего change.
3. Для применения получить статус и инструкции выбранного change и прочитать перечисленные в них артефакты. Не угадывать активный change при нескольких подходящих.
4. Прочитать затронутые capability, строки их статуса, соответствующий исходный код и проверки. Новая возможность может затронуть несколько исходных каталогов.
5. До редактирования назвать разрешённые файлы, сохраняемое поведение и проверку результата. Это описание границ, а не требование повторно просить разрешение на каждую обычную задачу уже согласованного change.
6. Выполнить только разрешённые задачи. Незнакомая служба, новая зависимость, изменение привилегий или поведения вне scope требуют остановки и уточнения.
7. Сообщить изменённое поведение или его отсутствие, проверки и известные ограничения. Не отмечать частичную задачу выполненной.

Назначение источников:

- Явная актуальная задача пользователя определяет область работы с учётом вышестоящих правил безопасности и среды.
- Основные спеки содержат действующий нормативный контракт. Согласованный change содержит только предлагаемые изменения этого контракта до синхронизации.
- Архитектура и принятые ADR объясняют решения; карта статуса показывает соответствие им, но не отменяет требования.
- Исходный код показывает реализацию, но не получает автоматически приоритет над требованием.
- Roadmap, примеры, памятки и `PLANS.md` не разрешают добавлять поведение самостоятельно.

При конфликте не выбирать источник молча: назвать требование, исходник и несовпадение. Если исправление входит в согласованный scope, выполнить его; если нет — зафиксировать пробел и запросить отдельное решение, не расширяя работу. Ошибку описания исправлять как описание; новую функцию предлагать как новый контракт.

Альтернатива «всегда верить коду» закрепляет дефекты, а «всегда считать спеку выполненной» скрывает их. Разделение намерения и свидетельств позволяет избежать обоих случаев.

### D3. Зафиксировать текущую архитектуру и отдельные правила развития

`docs/architecture.md` должен содержать следующие разделы с явными метками «существует», «архитектурное ограничение» и «будущий этап» там, где они необходимы:

1. **Текущая структура:** `shell.qml`, `modules/`, `components/`, `services/`, `config/`, `extra/hypr/`, `install.sh`; назначение каждого пути. Корневой `services/` сейчас содержит QML-объекты, а не демоны.
2. **Процессы:** один Quickshell для полного состава оболочки; Hyprland и платформенные службы — внешние процессы. Не гарантировать, что пользователь физически не может запустить второй экземпляр. Собственного менеджера сессии пока нет.
3. **Зависимости:** `shell.qml -> modules`, `modules -> components`, `modules -> services`, `services -> native API / optional adapters`. Указать, что стрелка означает зависимость, а обновления состояния возвращаются через свойства и события.
4. **Состояние и UI:** локальные фокус/наведение/выбор/черновик допустимы в представлении; подтверждённое системное состояние и операции принадлежат сервису. Отдельный адаптер создаётся при собственной ответственности, а не по обязательной схеме каталогов.
5. **Данные:** текущие пути из `config/Config.qml`, поставляемые QML-настройки, состояние обоев и записываемый профиль дисплеев. Разделение XDG config/state/cache/runtime — направление будущей миграции, не выполненное изменение путей.
6. **Интеграции и сбои:** аудио, яркость, ресурсы, сеть, батарея, уведомления, обои и Hyprland IPC; для каждой — API, данные/операции, события или опрос, доступные ошибки и источник в коде. Не приписывать всем сервисам уже реализованную общую модель `available/busy/error` или автоматическое переподключение.
7. **Установка:** область файлов, предупреждения, staging, резервирование, отсутствие переноса состояния; пакетный снимок в `extra/` не является воспроизводимым манифестом.
8. **Сессия:** какие команды декларирует пример; чего он не обеспечивает — проверенного запуска на обеих системах, управления готовностью/перезапуском/выходом, корректной настройки всех путей.
9. **Ресурсы:** существующие интервалы и условия опроса, ленивые окна, отсутствие численных бюджетов и связь с методикой будущих измерений.

ADR-0001 фиксирует уже существующее продуктовое решение. ADR-0002 фиксирует уточнение границ для дальнейшего развития; при применении явно связать его с известными отклонениями, не обозначать код полностью приведённым к этому решению. До применения оба решения находятся в данном предложении; будущие UWSM и XDG-миграция не получают статус принятых ADR.

### D4. Сохранить идентичность требований и исправить смысл

Дельты этого change модифицируют все 36 существующих требований в пяти capability. Сохранены пути, заголовки требований и все исходные имена сценариев; добавлены уточняющие сценарии. Это важно для валидатора и синхронизации: `MODIFIED` заменяет целый блок, а локальный валидатор запрещает потерю исходных сценариев.

Источником нового текста требований являются файлы `specs/*/spec.md` данного change. При применении не пересказывать их свободно и не менять сценарии ради прохождения проверки.

Различать два случая:

- Неподтверждённое обещание исходного baseline, например установка всех пакетов: уточняется область контракта, соответствующая существующей поставке; расширение поставки остаётся будущим этапом.
- Известное нарушение существующего требования, например заявленная поддержка markup при `Text.PlainText`: требование не удаляется, нарушение фиксируется. Данный change не исправляет UI и не отмечает этот сценарий пройденным.

После синхронизации отдельно заменить только `Purpose` основных спек следующими текстами; дельта существующей capability не переносит `Purpose`:

| Capability | Новый Purpose |
|---|---|
| `desktop-environment` | «Определить границы Custom DE как продукта, состав текущей поставки и ограничения платформы, не смешивая их с ещё не реализованными целями развития.» |
| `architecture` | «Определить проверяемые архитектурные ограничения рабочего окружения: ответственность компонентов, направление зависимостей, границы интеграций и ресурсной работы. Соответствие реализации учитывается отдельно в карте статуса требований.» |
| `shell` | «Определить пользовательские возможности оболочки Quickshell и их наблюдаемые результаты, включая ошибки и границы сохранения состояния. Наличие требования не означает, что все его сценарии уже проверены.» |
| `system-package-management` | «Определить текущий контракт установки QML-оболочки, внешние зависимости и ограничения развёртывания; не выдавать его за установщик всего DE или подтверждение совместимости целевых дистрибутивов.» |
| `session` | «Определить декларации существующего примерного профиля Hyprland, который не разворачивается установщиком оболочки. Сценарии исполнения требуют отдельно подготовленной сессии; успешная блокировка и полная переносимость не подтверждены проверкой текста.» |

Альтернатива немедленного дробления `shell` на множество capability увеличивает миграцию и вероятность потерять требования. Пять текущих путей сохраняются; выделение новой capability выполняется при соответствующем функциональном изменении.

### D5. Создать карту свидетельств, а не вторую спецификацию

В `docs/spec-status.md` сделать отдельную таблицу для каждой capability, по одной строке на каждое требование. Ключ — путь capability и точный заголовок требования, а не придуманный новый идентификатор в заголовке спеки.

Поля строки:

- требование со ссылкой на основную спеку;
- основание: код, декларация примера, принятое архитектурное решение или ранее принятый контракт;
- конкретный исходный файл и символ/блок либо ADR;
- соответствие: подтверждено чтением, известное несоответствие или не установлено;
- проверка: просмотр кода/документов, доступная команда или ручной сценарий; отдельно указать, выполнялась ли она;
- идентификатор пробела, если он есть.

Для требования с несколькими сценариями отдельно отметить непроверенные или нарушенные сценарии. Просмотр кода не обозначать как успешное runtime-испытание. Не ссылаться на несуществующий автоматический тест как на доказательство.

| G07 | Применение мониторов не имеет подтверждения пользователем с автоматическим возвратом | `MonitorService.qml` и `MonitorEditorState.qml`; кандидат нового поведения, не нарушение уже обещанного отката |
| G08 | Заявленная поддержка markup не соответствует отображению карточки | `bodyMarkupSupported: true` против `textFormat: Text.PlainText`; нарушенный сценарий уведомлений, не считать пройденным |
| G09 | Нет подтверждённой установки полного DE на обеих целевых системах | Нет package/deployment-слоёв и журнала соответствующих испытаний; продуктовая цель, а не доказанная поддержка |

Данные о пробелах имеют дату/ревизию. После будущего исправления сохранять краткую ссылку на исправившее изменение и проверку, а не оставлять устаревшее описание активным.

### D6. Сделать инструкцию агенту проверяемой

`AGENTS.md` остаётся на английском; проектные документы и пояснения спек — на русском, служебные заголовки OpenSpec сохраняются. Актуализировать пути `modules/...`, `services/Brightness.qml`, `config/Theme.qml`, импорт `qs.config`; не оставлять старые имена как действующие указания.

В `openspec/config.yaml` сохранить схему `spec-driven`. Контекст ограничить назначением проекта, фактической поставкой, оборудованием, языковой оговоркой и ссылками. В `rules` использовать существующие ключи артефактов `proposal`, `specs`, `design`, `tasks`:

- proposal: назвать scope/non-goals и изменяемые capability; не выдавать roadmap за разрешение;
- specs: источник требования, наблюдаемый результат, ошибки, сохранение идентичности существующих блоков; нормативный контракт отделён от статуса соответствия;
- design: разрешённые файлы/слои, реальные зависимости, привилегии и побочные эффекты, проверки и миграция;
- tasks: одна конечная работа на пункт, конкретные файлы, ожидаемый результат и проверка; не отмечать заблокированное выполненным.

Не требовать от документационного change выполнения runtime-испытаний всех давно существующих функций. Его критерий — точность описаний и честный учёт ограничений. Функциональное изменение не считается проверенным, если обязательная проверка недоступна.

В `docs/testing.md` сохранить полезные существующие ручные сценарии, но назвать их доступными процедурами, а не результатами уже выполненных испытаний. Исправить обещание безопасности при любой отсутствующей зависимости: обязательный QML-импорт отличается от отсутствующей батареи/службы. Число уведомлений указывать как настраиваемый предел с исходным значением пять. Не рекомендовать подменять `HOME` рабочего процесса для проверки установщика; будущая изоляция использует отдельную среду/учётную запись либо специально спроектированный целевой путь.

Формат отчёта о проверке: требование/сценарий, среда и ревизия, команда или действие, ожидаемый результат, фактический результат, статус `пройдено` / `не пройдено` / `не выполнялось` / `заблокировано`, причина ограничения. Недоступная проверка не становится успешной.

### D7. Последующие этапы имеют отдельные границы согласования

Roadmap не должен быть вторым `tasks.md`. Предлагаемый порядок:

1. **Текущий change:** документация, архитектурные ограничения и исправленный baseline.
2. **Безопасная установка и первые автоматические проверки:** определить поставляемые файлы, пользовательские данные, повторную установку, восстановление и изолированную среду; проверять установщик вместе с изменением его контракта.
3. **Пакеты и сессия:** выбрать проверяемые платформы/версии, источник пакетов, владельца процессов, блокировку и жизненный цикл; отдельно решить вопрос UWSM. Дефект блокировщика имеет высокий приоритет и может потребовать отдельного раннего исправления, не дожидаясь всей перестройки.
4. **Границы оболочки и данные:** устранять конкретные нарушения UI/сервисов, определить миграцию XDG; перенос исходников допускается после подготовки установщика и проверки импортов.
5. **Развитие возможностей и измерений:** отдельные capability по мере изменения, исправление уведомлений, безопасность изменения дисплеев, интеграционные проверки и ресурсные бюджеты на основе измерений.

Этапы 2–5 не получают флажки выполнения в данном change. Известный дефект можно исправлять отдельным согласованным изменением раньше; roadmap не должен блокировать необходимое исправление безопасности.

## Risks / Trade-offs

- Документы размножаются → каждому назначено одно место ответственности, указатель задаёт короткий маршрут чтения, таблица статуса не копирует требования.
- Уточнение baseline может скрыть регрессию → сохраняются идентичность требований и сценариев, основания изменений и известные несоответствия; поддержка markup не отменяется молча.
- Архитектурное ограничение ещё нарушается кодом → явно зафиксировать G01/G08 и другие релевантные пробелы; не объявлять весь DE приведённым к архитектуре.
- Чтение кода выглядит как тестирование → раздельные поля соответствия и фактически выполненной проверки; runtime не запускается в этом change.
- Документальная синхронизация может преждевременно выглядеть как реализация будущего этапа → переносить только подготовленные дельты, не требования будущих runtime-изменений.
- Работа затрагивает пользовательские незакоммиченные документы → повторно прочитать их перед редактированием, сохранить полезный текст, модельную пометку и исторический разбор.
- Зелёный OpenSpec validate создаёт ложную уверенность → дополнительно проверить комплектность всех пяти дельт, соответствие источникам, сохранность сценариев и область файлов.

## Migration Plan

1. При применении прочитать актуальные артефакты change и проверить изменения пользователя после планирования. Если исходники изменились так, что выводы неверны, уточнить affected-часть плана до её применения.
2. Создать указатель, архитектуру и два ADR, сократить продуктовый контекст; затем создать карту требований и roadmap. Переносить смысл из старого контекста, не оставлять две действующие архитектуры.
3. Обновить инструкции, тестирование, README и статус `PLANS.md`; не менять исторический разбор и модельную пометку.
4. Синхронизировать пять дельт с основной спецификацией через навык `openspec-sync-specs`, затем точечно изменить `Purpose` по D4. Это входит в область применения данного change, но не разрешает архивировать его автоматически.
5. Проверить все ссылки, отсутствие устаревших инструкций, соответствие карте требований и команды ниже. Только после этих проверок завершить задачи документационного этапа.

Проверки при применении:

```bash
openspec validate "clarify-de-architecture-and-specs" --strict
openspec validate --specs --strict
git diff --check
bash -n "install.sh"
git status --short
```

`bash -n` — только синтаксическая проверка неизменённого установщика. Новые незакоммиченные файлы проверять отдельно через `git diff --no-index --check -- /dev/null "<конкретный-файл>"`, поскольку обычный `git diff --check` их не охватывает. Проверка ссылок должна обходить реальные локальные Markdown-ссылки, а будущие пути в roadmap должны быть помечены как будущие, не оформлены как существующие ссылки.

Дополнительно сравнить списки заголовков требований и исходных сценариев до/после синхронизации: пять capability, 36 требований, ни один исходный сценарий не потерян. Все изменённые сценарии должны иметь основание в тексте этого change и карте статуса. Список изменённых файлов должен ограничиваться областью proposal и артефактами change.

Откат документального изменения — обратный patch только к собственным правкам с сохранением пользовательских изменений; никакого сброса рабочей копии. Установка и живая сессия не затронуты, поэтому откат не требует изменения машины.

Для последующих этапов остаются выбор ветки Debian и условий поддержки, UWSM или другой владелец сессии, формат пользовательских настроек, способ изоляции установщика и тестовый framework. Эти решения не принимать в данном change и не закладывать как уже существующие зависимости.
