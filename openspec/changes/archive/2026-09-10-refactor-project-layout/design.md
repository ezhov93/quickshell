## Context

Текущий Git-корень уже содержит `shell/`, `docs/`, `openspec/`, `extra/`, `install.sh`, `scripts/` и editor metadata. `shell/` — самостоятельный runtime Quickshell с `shell.qml`, `qmldir`, `config/`, `components/`, `services/` и `modules/`. Текущий установщик копирует только этот runtime в `~/.config/quickshell`.

## Goals / Non-Goals

**Goals:**

- Разделить продуктовые слои на понятные верхнеуровневые границы.
- Не смешивать QML-сервисы внутри процесса Quickshell с будущими системными сервисами.
- Сделать будущие package/session/deployment изменения локальными и проверяемыми.
- Сохранить возможность запускать и устанавливать текущий shell независимо от ещё не реализованных слоёв.

**Non-Goals:**

- Не реализовывать полную установку DE.
- Не создавать systemd units, package manifests или собственные daemon без отдельных задач.
- Не менять UI, IPC, session keybinds или runtime-поведение shell.
- Не переносить `extra/hypr/` автоматически в рамках одного структурного решения.

## Decisions

### 1. `shell/` — отдельный runtime Quickshell

В `shell/` находятся только файлы, которые нужны Quickshell: entrypoint, manifests, общие config/components/services и модули. `install.sh` явно ограничен этим каталогом.

Альтернатива — оставить shell в корне — отвергнута: она смешивает runtime с документацией и deployment-логикой.

### 2. `configs/` содержит декларативные конфигурации

Здесь должны находиться конфигурации Hyprland, приложений и пользовательские шаблоны, когда они перестанут быть только примером. Runtime Quickshell не импортирует конфигурации из этого слоя напрямую без определённого контракта.

`extra/` сохраняется как переходная область для материалов, которые ещё не имеют принятого deployment-контракта; его перенос требует отдельной проверки владельца и путей.

### 3. `packages/` описывает зависимости, но не устанавливает их сам по себе

Package manifests и различия Arch/Debian принадлежат `packages/`. Они не должны импортироваться shell-кодом и не дают разрешения менять текущий `install.sh`, пока не появится отдельный deployment change.

### 4. `system/` и `services/` имеют разные границы

`system/` предназначен для systemd user units, portals, session wiring и других деклараций внешней системы. `services/` — для собственных долгоживущих сервисов/демонов проекта, если они будут обоснованы. QML singleton-сервисы остаются в `shell/services/` и не переносятся в корневой `services/`.

Новый daemon требует отдельного обоснования привилегий, lifecycle, отказов и стоимости ресурсов.

### 5. `install/` и `scripts/` не смешиваются

`install/` содержит deployment-профили и вспомогательные данные установки; `scripts/` — разработческие и проверочные скрипты, не являющиеся runtime. Корневой `install.sh` может оставаться совместимым entrypoint до выделения deployment-слоя отдельной задачей.

### 6. Зависимости направлены от deployment к слоям

```text
install/ ───────> packages/  system/  configs/
                       │        │        │
                       └────────┴────────┴──> shell/
docs/ openspec/ ─────> описывают и проверяют все слои
scripts/ ────────────> проверяют слои, но не становятся runtime-зависимостью
```

`shell/` не должен зависеть от installer или package manager. Системные конфигурации могут запускать shell, но не должны встраивать его внутреннюю QML-архитектуру.

## Risks / Trade-offs

- [Риск] Перенос путей ломает документацию и команды → [Митигация] мигрировать слой за слоем и проверять ссылки, manifests и `install.sh` после каждого шага.
- [Риск] Пустые каталоги создадут иллюзию реализованных слоёв → [Митигация] создавать каталог только вместе с первым ответственным файлом или отдельным change.
- [Риск] Корневой `services/` будет принят за QML-сервисы → [Митигация] явно документировать различие с `shell/services/`.
- [Риск] `extra/` останется второй системой размещения → [Митигация] считать его переходной зоной и переносить содержимое отдельными задачами с проверкой владельца.

## Migration Plan

1. Утвердить дерево и таблицу ответственности в документации.
2. Провести инвентаризацию `extra/`, корневых файлов и `scripts/`, назначив каждому файлу целевой слой или статус переходного.
3. Отдельным change перенести конфигурации в `configs/`, сохранив пути и возможность отката.
4. Отдельными change добавить package manifests, system/session материалы и deployment-слой.
5. После каждого переноса обновлять ссылки, проверки и карту статуса.

Откат структурного шага выполняется возвратом файлов в прежние пути в одной ревизии; пользовательская сессия и установленный `~/.config/quickshell` не изменяются агентом.
