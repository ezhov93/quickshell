## Context

В репозитории есть локальная `main`, совпадающая с `origin/main`; опубликованных тегов нет. CI, branch protection и формальный contribution guide пока не обнаружены. OpenSpec уже связывает change с задачами, поэтому task ID можно использовать в имени feature-ветки.

## Goals / Non-Goals

**Goals:**

- разделить разработку, интеграцию и последний релиз;
- сделать связь OpenSpec task → feature branch → merge проверяемой;
- выпускать rolling-релизы без долгоживущих release-веток;
- сохранить воспроизводимость версии по Git-тегу.

**Non-Goals:**

- не менять историю Git автоматически;
- не удалять `main` и не менять remote без отдельного применения миграционного шага;
- не создавать CI/CD, если отдельная задача не определит платформу и проверки;
- не вводить package/runtime версии и не менять код продукта.

## Decisions

### 1. Роли веток

- `develop` — постоянная ветка интеграции завершённых feature-веток;
- `main` — постоянная ветка последнего стабильного релиза;
- `feature/<change-name>` — короткоживущая ветка одного OpenSpec change от актуального `develop`; все пункты `tasks.md` этого change выполняются в ней;
- `hotfix/<version>-<slug>` — срочное исправление от `main`, после релиза возвращается и в `develop`.

`main` уже является текущей веткой и сохраняет роль стабильной ветки. Отдельная ветка `master` не создаётся и не используется.

### 2. Модель rolling-релиза

Разработка вливается в `develop` небольшими изменениями. Когда набор изменений готов, `develop` fast-forward или merge-коммитом продвигается в `main`; на commit `main` создаётся аннотированный тег `vMAJOR.MINOR.PATCH`. Release-ветки не создаются: следующий релиз снова формируется из `develop`.

Версия определяется тегом, теги не переписываются и не удаляются. `MAJOR` повышается при несовместимом изменении, `MINOR` — при совместимой возможности, `PATCH` — при исправлении/рефакторинге без изменения контракта. До первого релиза допустим `v0.y.z`.

### 3. Правило feature-ветки

Для OpenSpec change `refactor-project-layout` имя ветки будет `feature/refactor-project-layout`. Подветки для пунктов `tasks.md` не создаются; отдельный change получает отдельную feature-ветку.

### 4. Merge и защита

В `develop` и `main` запрещаются прямые push. Merge выполняется через review/PR после проверки соответствующей задачи, `openspec validate`, проектных проверок и ручных условий. Feature-ветка удаляется после merge. `main` дополнительно требует успешный release checklist и тег на том же commit.

В текущем репозитории CI и protection не доказаны, поэтому сначала правила применяются документально и локальными проверками; автоматизация добавляется отдельным change.

### 5. Миграция текущего Git-состояния

Не переписывать историю. На текущем commit создаётся только `develop`; существующая `main` сохраняется как ветка стабильного релиза. `master` не создаётся. Remote и default branch не меняются автоматически.

## Risks / Trade-offs

- [Риск] Две активные линии создадут расхождение → [Митигация] main меняется только через релиз из develop, hotfix вливается обратно.
- [Риск] Неправильный тег создаст неверный релиз → [Митигация] аннотированные SemVer-теги и checklist перед публикацией.
- [Риск] Политика не будет enforced без CI/branch protection → [Митигация] явно считать автоматическую защиту отдельным незавершённым этапом.
- [Риск] Неправильная публикация changelog создаст неясный состав релиза → [Митигация] держать `Unreleased` сверху, переносить записи в датированную версию только при релизе и не редактировать опубликованные разделы.

## Migration Plan

1. Зафиксировать правила в `docs/git-workflow.md`, связать их с OpenSpec workflow и добавить корневой `CHANGELOG.md`.
2. Создать локальный `develop` от текущего проверенного commit без изменения истории.
3. Проверить remote, default branch, права и возможность branch protection; не менять их автоматически.
4. Применять новые задачи через feature-ветки и PR в `develop`.
5. Выполнить первый rolling-релиз merge `develop` → `main`, обновить changelog и создать первый согласованный тег.

Откат миграции веток выполняется удалением только новых локальных refs после проверки; история commit и рабочие файлы не переписываются.
