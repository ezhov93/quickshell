# Стратегия тестирования LPDE

Этот документ описывает, как проверять LPDE при изменениях. Он разделяет доступные процедуры и будущую тестовую инфраструктуру. Наличие процедуры ниже не означает, что она уже выполнялась для текущей ревизии; фактические результаты записываются отдельно.

## Цели тестирования

Тестирование должно подтверждать не только отсутствие синтаксических ошибок, но и целостность рабочего окружения:

- shell запускается в сессии Hyprland;
- модули реагируют на пользовательские действия;
- интеграции корректно работают с внешними компонентами;
- предусмотренная деградация работает при недоступности конкретной внешней службы или устройства;
- конфигурация устанавливается воспроизводимо;
- новые изменения не добавляют лишний polling, фоновые процессы или заметную нагрузку на слабое оборудование.

## Текущее состояние

Сейчас проект запускается непосредственно в Quickshell и не имеет build step, автоматического test framework или отдельного каталога `tests/`. Поэтому текущая стратегия состоит из статических проверок, проверки установщика и ручных runtime/integration-проверок.

Ниже автоматические проверки не следует воспринимать как уже реализованные: раздел «Будущие проверки» описывает направления развития.

## Доступные процедуры проверки

Команды и ручные сценарии этого раздела существуют как способы проверки. Они не являются постоянным заявлением «тест пройден». В отчёте нужно указывать фактический запуск и результат.

### OpenSpec и документация

Для проверки спецификаций и документации используются:

```bash
openspec validate --specs --strict
git diff --check
```

`openspec validate` проверяет структуру baseline-спеков, но не соответствие кода требованиям. `git diff --check` выявляет whitespace-ошибки только в изменениях, известных Git; новые untracked-файлы нужно проверять отдельно.

### Установщик

При изменении `install.sh` проверяется синтаксис:

```bash
bash -n "install.sh"
```

Изолированная ручная проверка установщика должна подтверждать:

- запуск от обычного пользователя без `sudo`;
- отказ при запуске от root;
- установку в `~/.config/quickshell/`;
- создание backup существующей конфигурации;
- сохранение структуры QML-файлов и `qmldir`;
- отсутствие запуска shell и изменения Hyprland во время установки;
- корректное сообщение об отсутствующих зависимостях.

Проверять установку следует в отдельной среде или отдельной тестовой учётной записи. Текущий скрипт жёстко использует домашний каталог процесса, поэтому произвольная подмена `HOME` в рабочей сессии не считается безопасным тестовым интерфейсом. Нельзя заменять реальную конфигурацию пользователя ради проверки; поддерживаемый override целевого пути нужно сначала отдельно спроектировать.

### Запуск shell

После изменений Quickshell нужно запустить конфигурацию в сессии Hyprland:

```bash
quickshell -p "$HOME/.config/quickshell"
```

Проверяется:

- отсутствие ошибок QML при запуске;
- создание всех модулей из `shell.qml`;
- отсутствие ошибок при закрытии и повторном открытии окон;
- корректное применение общей темы;
- отсутствие регрессий при подключении отдельных модулей.

### Изолированная offscreen-самопроверка Quickshell

До ручной проверки можно проверить QML-сервисы, импорты и компоненты, которым не нужен оконный backend. Эта процедура не запускает Hyprland, не использует пользовательский `~/.config/quickshell` и не заменяет runtime-проверку `PanelWindow`.

Проверки структуры репозитория должны отдельно подтверждать, что `shell/` остаётся самостоятельным runtime, а будущие `configs/`, `packages/`, `system/`, корневой `services/` и `install/` не объявлены реализованными только по плану. Материалы в `extra/` проверяются как переходные примеры до их отдельной миграции.

1. Создать временное дерево и скопировать в него только runtime-каталоги:

```bash
check_root=$(mktemp -d /tmp/quickshell-offscreen.XXXXXXXX)
mkdir -p "$check_root/config" "$check_root/runtime" "$check_root/cache"
chmod 700 "$check_root/runtime"
cp -a shell/qmldir shell/config shell/components shell/services shell/modules "$check_root/config/"
```

2. Создать в `$check_root/config/shell.qml` минимальный harness. Он импортирует изменённые локальные модули и обращается к проверяемым singleton-сервисам. Неоконные компоненты можно создать внутри `Item`, передав все `required property`. Типы на основе `PanelWindow` в offscreen-harness не создаются.

Пример для сервисов Bar:

```qml
import Quickshell
import QtQuick

import qs.modules.Bar.services

Scope {
  property var workspaceService: WorkspaceService
  property var mediaService: MediaService
  property var trayService: TrayService
}
```

3. Запустить harness без графического display и с отдельными XDG runtime/cache:

```bash
timeout 5s env -u DISPLAY -u WAYLAND_DISPLAY \
  QT_QPA_PLATFORM=offscreen \
  QT_QPA_PLATFORMTHEME= \
  XDG_CACHE_HOME="$check_root/cache" \
  XDG_RUNTIME_DIR="$check_root/runtime" \
  quickshell -p "$check_root/config" --no-color
```

Результат считается пройденным, если журнал содержит `INFO: Configuration Loaded`, не содержит ошибок QML/import/type и процесс работает до `timeout` (код 124 допустим). Предупреждения о намеренно недоступных D-Bus, MPRIS, SystemTray или Hyprland записываются как ограничения среды, а не скрываются.

`No PanelWindow backend loaded` при попытке создать полный shell без Wayland означает `заблокировано`, а не успешную проверку и не доказанную регрессию. Ошибки вида `Type ... unavailable`, `... is not a type`, ошибки parser/binding и отсутствие `Configuration Loaded` означают `не пройдено`.

Если проверяется временная копия настоящего `shell.qml`, pragma `QT_QPA_PLATFORMTHEME=gtk3` можно удалить только из временного файла, иначе GTK попытается открыть пользовательский display. Исходный `shell.qml` менять ради offscreen-проверки нельзя. Агент не должен запускать, блокировать или перезапускать пользовательскую графическую сессию.

### IPC и клавиатурное управление

Изменённые IPC targets проверяются при запущенном shell. Используются команды, которые уже описаны в проекте:

```bash
qs ipc call launcher toggle
qs ipc call wallpaper toggle
qs ipc call monitors toggle
qs ipc call monitors refresh
qs ipc call notifications dnd_toggle
qs ipc call idle enable
qs ipc call idle disable
qs ipc call bar toggle
```

Для каждого изменённого target проверяется открытие, закрытие, повторный вызов и отсутствие ошибки при недоступном состоянии.

### Ручные проверки модулей

Проверять нужно только изменённые модули и связанные с ними общие сервисы.

#### Bar

- панель отображается на доступных экранах;
- рабочие пространства и активное окно обновляются;
- отображаются системный трей, медиа, громкость, яркость, сеть, батарея, раскладка и время;
- скрытие панели останавливает связанные polling-механизмы, где это предусмотрено текущей реализацией;
- сетевые настройки открываются через настроенную терминальную команду;
- окно сетевых настроек имеет class `lpde-nmtui`, открывается floating, не имеет внутренних полей Foot и не влияет на обычные окна Foot;
- у обычного Foot сохраняется глобальный `pad`, а локальный override `main.pad=0x0` применяется только к `nmtui`;
- размер floating-окна меняется перетаскиванием за границу, а при перемещении/изменении размера snap учитывает зазоры до окон и краёв монитора.

Для проверки сетевого окна владелец подготовленной графической сессии может использовать:

```bash
hyprctl clients
```

Агент не запускает и не перезапускает графическую сессию; результат этих проверок фиксируется как ручной результат владельца окружения.

#### AppLauncher

- поиск работает по имени, общему имени, keywords и категориям;
- стрелки и Tab перемещают выбор;
- Enter/Return запускает выбранное приложение;
- Escape закрывает launcher;
- повторное открытие создаёт корректное состояние поиска.

#### Notifications

- уведомления отображаются в правильной области;
- поддерживаются urgency, изображения, actions и timeout;
- одновременно удерживается не больше настроенного предела уведомлений (текущее значение по умолчанию — пять);
- обычные уведомления при отсутствии hover закрываются по таймеру, критические — нет;
- тело с markup проверяется отдельно: сейчас сервер заявляет поддержку, но карточка отображает plain text, поэтому этот сценарий нельзя отмечать пройденным;
- работают закрытие карточки; `dismiss_all` и его hotkey отложены для отдельной проверки необходимости;
- Do Not Disturb не показывает новые уведомления.

#### Osd, Audio и Brightness

- OSD появляется после изменения громкости или яркости;
- индикатор автоматически скрывается после настроенного timeout;
- громкость обновляется через PipeWire;
- яркость изменяется через настроенное устройство и `brightnessctl`;
- отсутствие доступного устройства не приводит к падению shell.

#### Wallpaper

- сканируются настроенные каталоги и допустимые форматы изображений;
- список ограничивается настроенным максимумом;
- левый клик применяет обои, правый открывает предпросмотр;
- успешно применённый wallpaper сохраняется;
- сохранённый wallpaper восстанавливается после запуска;
- ошибки применения и ошибки сохранения показываются отдельно.

#### MonitorManager

- список мониторов читается через Hyprland socket;
- изменяются режим, частота, координаты, масштаб, поворот, зеркалирование и состояние выхода;
- применение выполняется пакетом;
- после применения выполняется повторное чтение и проверка;
- конфигурация сохраняется только после успешной проверки;
- ошибка записи оставляет окно редактора открытым.

Применение настроек мониторов меняет живую конфигурацию дисплеев и может перезаписать `~/.config/hypr/monitors.conf` или `monitors.lua`. Поэтому эту проверку следует выполнять только в контролируемой сессии и учитывать возможность восстановления предыдущей конфигурации.

#### IdleInhibitor

- `enable` и `disable` через IPC остаются доступными для будущей отдельной проверки; hotkey `idle toggle` отложен;
- badge появляется при изменении состояния;
- настроенная idle-политика сессии учитывает Wayland idle-inhibit; явная блокировка пользователем проверяется отдельно и не должна считаться запрещённой;
- после перезапуска shell режим снова выключен.

### Проверки зависимостей и отказоустойчивости

Для изменённой интеграции нужно проверить как доступный, так и недоступный внешний компонент, если это возможно без изменения системы:

- PipeWire недоступен;
- UPower не предоставляет батарею;
- NetworkManager не сообщает активное подключение;
- hyprpaper ещё не запущен;
- отсутствует устройство подсветки;
- Hyprland socket недоступен;
- отсутствует файл сохранённой конфигурации.

Ожидаемый результат должен быть явно указан в соответствующей OpenSpec-спеке: скрытый индикатор, значение `N/A`, сообщение об ошибке или безопасное отключение возможности.

Отсутствие внешнего устройства или запущенной службы не равно отсутствию обязательного QML-импорта. Например, отсутствие батареи может штатно скрыть индикатор, а отсутствие импортируемого модуля Quickshell способно остановить загрузку всей оболочки. Без отдельной реализации и проверки нельзя обещать мягкую деградацию для любой зависимости.

## Проверки производительности

Текущая реализация уже ограничивает часть фоновой работы:

- polling ресурсов активен только при видимой панели;
- сетевой fallback polling активен только при необходимости и видимой панели;
- окна launcher, wallpaper и monitor manager загружаются лениво;
- состояние CPU, памяти и температуры читается напрямую из `/proc` и `/sys`;
- для системных изменений используются события, где они доступны.

При изменениях нужно вручную проверять, что новая логика не создаёт постоянный polling или новый фоновый процесс без обоснования. Численные CPU/RAM-бюджеты пока не определены, поэтому их нельзя выдавать за существующие автоматические критерии.

## Будущие проверки

Следующие направления можно добавить постепенно. Они пока не реализованы и не должны считаться частью текущего test coverage.

### Автоматическая проверка чистой логики

Выделить небольшие функции, не зависящие от Wayland и живых системных сервисов, и покрыть их тестами:

- парсинг режимов мониторов;
- построение конфигурации мониторов;
- расчёт использования CPU и памяти;
- сортировку и фильтрацию приложений;
- фильтрацию файлов обоев;
- разбор сетевых маршрутов.

Конкретный test framework пока не выбран.

### Изолированная проверка установщика

Добавить тесты, которые проверяют backup, staging, повторную установку, отказ root и отсутствие изменения исходных файлов в отдельной среде/учётной записи либо через предварительно спроектированный параметр целевого пути. Тесты не должны подменять или затрагивать реальный `~/.config` пользователя.

### Integration tests

В будущем можно добавить контролируемые проверки границ с внешними системами:

- D-Bus-сервисы UPower, NetworkManager и BlueZ;
- PipeWire и WirePlumber;
- Hyprland IPC;
- системные session units.

До выбора mock или test-container подхода нельзя утверждать, что такие тесты существуют или запускаются в CI.

### Smoke-тесты запуска shell

Можно добавить автоматизированный smoke-тест, который запускает минимальный shell и проверяет загрузку модулей, IPC targets и отсутствие QML ошибок. Реализация должна учитывать доступность Wayland/Hyprland и не должна требовать запуска полноценной пользовательской сессии без отдельного изолированного окружения.

### Проверка Arch и Debian

После появления отдельных package/deployment слоёв можно добавить проверки установки на Arch Linux и Debian. До этого текущая проверка dependency list отражает в основном Arch-окружение и не является полноценной проверкой Debian.

### Измерение ресурсов

Позже стоит зафиксировать воспроизводимый способ измерять:

- idle CPU;
- потребление памяти;
- количество фоновых процессов;
- частоту polling;
- время запуска shell.

Пороговые значения должны быть согласованы отдельно, чтобы не превращать произвольные числа в неподтверждённые требования.

## Формат отчёта о проверке

Для каждой обязательной проверки записываются:

| Поле | Содержание |
|---|---|
| Требование/сценарий | Точное имя из OpenSpec |
| Среда | Дистрибутив, версии значимых компонентов, оборудование и ревизия проекта |
| Процедура | Команда или последовательность действий |
| Ожидается | Наблюдаемый результат из сценария |
| Получено | Фактический результат без догадок |
| Статус | `пройдено`, `не пройдено`, `не выполнялось` или `заблокировано` |
| Ограничение | Причина отсутствующей или неполной проверки |

Недоступная обязательная проверка получает статус `не выполнялось` или `заблокировано`, но не `пройдено`. Успешная статическая проверка не заменяет runtime-сценарий.

## Как связывать тесты с OpenSpec

Для каждого нетривиального изменения:

1. В `spec.md` описываются наблюдаемые acceptance-сценарии, включая ошибки и недоступные зависимости.
2. В `design.md` фиксируется стратегия проверки и границы интеграционных тестов.
3. В `tasks.md` записываются конкретные команды, ручные проверки и ожидаемый результат.
4. Реализация считается готовой только после выполнения задач и проверки связанных сценариев.
5. При архивировании change результаты проверки должны быть отражены в итоговом описании изменения.

Для документационных изменений нужно сверить утверждения с кодом, проверить локальные ссылки, выполнить OpenSpec validation и whitespace-проверки. Для изменений `install.sh` дополнительно выполняется `bash -n "install.sh"`, но это только синтаксис. Для изменений shell обязательна ручная проверка в подходящей Hyprland-сессии; если среда недоступна, это явно отражается в отчёте и задача не считается проверенной по этому критерию.
