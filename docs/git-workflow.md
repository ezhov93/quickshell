# Git-процесс LPDE

Проект использует rolling-модель: разработка накапливается в `develop`, а `main` содержит последний стабильный релиз. История не переписывается, опубликованные теги не изменяются.

## Ветки

| Ветка | Назначение | Основание | Результат |
|---|---|---|---|
| `main` | Последний стабильный релиз | текущий стабильный commit | релизный тег |
| `develop` | Интеграция разработки | актуальный `main` при создании, затем предыдущий `develop` | проверенный набор изменений |
| `feature/<change-name>` | Один OpenSpec change | актуальный `develop` | PR в `develop` |
| `hotfix/<version>-<slug>` | Срочное исправление стабильного релиза | `main` | merge в `main` и обратно в `develop` |

Отдельные ветки для пунктов `tasks.md` не создаются. Все пункты одного OpenSpec change выполняются в его единственной feature-ветке.

Пример:

```text
feature/refactor-project-layout
```

## Рабочий цикл OpenSpec change

1. Создать или выбрать OpenSpec change.
2. Обновить `develop`.
3. Создать `feature/<change-name>` от `develop`.
4. Выполнять пункты `tasks.md` в этой ветке и отмечать их после проверки.
5. Выполнить проверки change и ручные проверки владельца сессии.
6. Открыть PR в `develop`, указав change, задачи, проверки и известные пробелы.
7. После merge удалить feature-ветку.

Прямые push в `develop` и `main` запрещены политикой проекта. Пока remote protection не настроен, это правило выполняется вручную.

## Rolling-релиз

Релиз выполняется без release-ветки:

```text
feature/<change> → develop → main → vMAJOR.MINOR.PATCH
```

Перед переносом `develop` в `main` требуется release checklist, зелёные проверки и обновлённый `CHANGELOG.md`. Тег создаётся на том же commit `main` и является аннотированным.

- `MAJOR` — несовместимое изменение контракта;
- `MINOR` — новая совместимая возможность;
- `PATCH` — исправление, документация или рефакторинг без изменения контракта.

До первого стабильного релиза используется `v0.y.z`. Теги не переписываются и не удаляются.

## Hotfix

1. Создать `hotfix/<version>-<slug>` от `main`.
2. Исправить проблему и выполнить проверки.
3. Влить hotfix в `main`, обновить changelog и создать следующий patch-тег.
4. Влить тот же hotfix в `develop`, чтобы исправление не потерялось.

## Changelog

Корневой [`CHANGELOG.md`](../CHANGELOG.md) ведётся по [Keep a Changelog 1.1.0](https://keepachangelog.com/en/1.1.0/). Новые изменения сначала записываются в `Unreleased`, затем при релизе переносятся в датированный раздел версии.

Используются категории `Added`, `Changed`, `Deprecated`, `Removed`, `Fixed`, `Security`. Опубликованные разделы не переписываются задним числом.

## Ограничения текущего репозитория

В репозитории пока нет опубликованных тегов, CI и подтверждённой branch protection. Создание локальных веток не публикуется автоматически; remote и его default branch меняются только отдельным явно подтверждённым действием.
